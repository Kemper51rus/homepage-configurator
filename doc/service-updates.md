# Информатор обновлений сервисов

Функция добавляет на карточку сервиса бейдж доступного обновления и модальное
окно запуска. Карточка не содержит команд или секретов: Docker-контейнер
выбирается из автоматически обнаруженного списка.

## Карточка

Настройка выполняется в визуальном редакторе сервиса или вручную:

```yaml
- Медиа:
    - Jellyfin:
        href: http://media.example.test:8096/
        serviceUpdate:
          type: docker
          source: docker-media
          target: jellyfin
```

`source` — имя штатного подключения из `docker.yaml`, `target` — найденное имя
контейнера. Вручную эти значения вводить не требуется: редактор сохраняет их
после выбора из списка.

Поддерживаемые режимы:

- `docker` — встроенное обнаружение и обновление образов. Штатные подключения
  работают через Docker Engine API, а Docker внутри LXC — через ограниченный
  исполнитель Proxmox;
- `lxc` — обнаружение контейнеров и их сетевых интерфейсов через штатный
  `proxmox.yaml`. Для системных пакетов используется один ограниченный
  исполнитель на узле Proxmox; устанавливать агент в каждый LXC не требуется.

## Docker-подключения

Конфигуратор читает штатный `docker.yaml` Homepage и отдельный серверный
`service-update-sources.yaml`. Второй вариант не включает автоматическое
создание карточек Homepage из Docker labels и подходит, когда подключение нужно
только для updater:

```yaml
version: 1
docker:
  docker-media:
    host: 192.0.2.10
    port: 2375
```

Штатный вариант также поддерживается:

```yaml
docker-media:
  host: 192.0.2.10
  port: 2375
```

Также поддерживаются socket, TLS и headers, которые уже поддерживает Homepage.
API никогда не принимает адрес Docker-хоста из браузера: клиент передаёт только
имя allowlisted-подключения и имя реально обнаруженного контейнера.

Если в Homepage уже настроен `proxmox.yaml` и установлен ограниченный helper,
конфигуратор опрашивает каждый работающий LXC через `pct exec`. Все найденные
Docker-контейнеры автоматически появляются отдельными целями с указанием LXC и
VMID. Порт `2375` для этого не нужен, Docker API не публикуется в сеть, а
ручные подключения из `docker.yaml` продолжают работать и имеют приоритет над
дубликатами автоматического списка.

При проверке backend выполняет pull тега и сравнивает ID загруженного образа с
образом работающего контейнера. При обновлении старый контейнер останавливается
и временно переименовывается, новый создаётся с прежними volumes, ports,
environment, restart policy и network aliases. Если новый контейнер не
запускается или не проходит healthcheck, выполняется rollback.

## Системные обновления LXC

Proxmox REST API показывает LXC и их интерфейсы, но не предоставляет выполнения
команд внутри LXC. Поэтому конфигуратор использует отдельную SSH-пару и
фиксированный helper `scripts/proxmox-lxc-updater.sh` на узле Proxmox. Ключ
root ограничивается в `authorized_keys` по адресу Homepage, `restrict` и forced
command; входной запрос может содержать только системную операцию LXC либо
`docker-discover`, `docker-check`, `docker-update` со строго проверенными именем
узла, числовым VMID и именем контейнера. Этот ключ не может открыть произвольную
shell-сессию или переадресовать порт.

Закрытый ключ и `known_hosts` хранятся только на сервере Homepage:

```text
config/service-update-proxmox/id_ed25519
config/service-update-proxmox/known_hosts
```

Проверка обновляет метаданные `apt` или `apk` и возвращает количество
обновляемых системных пакетов. Перед установкой helper пытается создать snapshot
LXC. Если snapshot недоступен, например из-за bind-mount, создаётся
`vzdump`-backup корневой системы на активном backup-хранилище с наибольшим
свободным местом. Сначала используется online-backup, затем fallback с кратким
`suspend`. Обновление запускается только после успешной защитной копии.

Обновления ОС LXC и приложений внутри Docker считаются разными слоями. Цель LXC
показывает количество вложенных Docker-контейнеров, но не перезапускает их
скрытно вместе с пакетами. Каждое Compose-приложение появляется отдельной
Docker-целью: helper загружает новый образ, создаёт защитную копию LXC и
выполняет `docker compose pull/up` только для выбранного сервиса. Контейнер без
безопасных Compose-меток обнаруживается, но требует ручного сценария обновления.

Программы, установленные вручную в `/opt`, из исходников или собственным
install-скриптом, не считаются системными пакетами и требуют специализированного
updater.

## Ручные runner-цели

`service-updates.yaml` остаётся для нестандартных сервисов и LXC, которым нужен
специализированный сценарий:

```yaml
version: 1
targets:
  jellyfin:
    label: Jellyfin
    type: docker
    runner: jellyfin
  recipes:
    label: Мои рецепты
    type: lxc
    runner: recipes
```

Значение `runner` — только имя файла. Абсолютные пути и `..` не разрешены.
Исполняемые файлы находятся рядом в `service-update-runners/`.

## Runner-протокол

Runner вызывается напрямую, без shell, с одним аргументом:

```text
service-update-runners/jellyfin check
service-update-runners/jellyfin update
```

Последняя непустая строка stdout должна быть JSON:

```json
{
  "state": "available",
  "updateAvailable": true,
  "currentVersion": "1.0.0",
  "latestVersion": "1.1.0",
  "message": "Доступен новый образ",
  "releaseNotes": "Необязательное описание"
}
```

После успешного `update` runner возвращает `state: success` и установленную
версию. Ненулевой exit code считается ошибкой; конец stderr показывается в
модальном окне. Вывод ограничен 64 KiB, проверка — 30 секундами, обновление —
30 минутами.

Нестандартный runner должен сам:

- проверять конкретную allowlisted-цель;
- выполнять backup при необходимости;
- устанавливать обновление;
- перезапускать только ожидаемый сервис;
- проверять его здоровье;
- возвращать корректный exit code.

Не следует делать один runner, принимающий hostname, путь или shell-команду из
браузера. Для каждой цели используется отдельная запись и фиксированный
исполняемый файл.
